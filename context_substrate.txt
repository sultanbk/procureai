System Overview
SynaptAI is a context substrate layer that converts unstructured documents into a queryable knowledge graph. It combines graph databases, vector stores, and LLM-driven extraction to enable both structural traversal and semantic search over your data.

📐 Architecture
💡
Every node in the graph has an embedding signature stored in the GN index with a direct Neo4j ID link — enabling semantic search that resolves instantly to graph nodes without fuzzy matching.
🔗
Neo4j
Concept Graph
Entities, concepts, propositions, procedures as DAGs, and relationships between them. The structural backbone.
📄
Milvus KS
Knowledge Store
Embedded document chunks for semacantic text search. Raw source material indexed by meaning.
📋
Milvus PS
Procedural Store
Embedded procedure intents for SOP retrieval. Find the right procedure by describing what you need.
🧠
Milvus GN
Graph Node Index
Embedded node signatures with direct Neo4j IDs. Bridges semantic search and graph traversal.

🔑 Key Concepts
Concept	Description
Provider	An isolated knowledge base. Each provider has its own Neo4j subgraph and Milvus collections.
Semantic Resolution	When an entity is extracted, its embedding is compared against existing nodes. If similarity > 0.85, it merges.
Unified Extraction	One LLM call per chunk extracts entities, concepts, relationships, and propositions together.
Extraction Density	Controls how many nodes/edges the LLM extracts per chunk: low (3-5), medium (5-10), or high (comprehensive).
SOP as DAG	Standard Operating Procedures are stored as Directed Acyclic Graphs with PRECEDES edges.
Reasoning Subgraph	When querying, the system returns the exact nodes and edges it traversed to answer the question.
Authentication & Access
Access to the Admin Console is gated by an email + password account secured with a one-time passcode (OTP), with optional Microsoft / SAML single sign-on. Roles control what each user can do.

🎚️ Extraction Density
Controls how much the Knowledge Service extracts per chunk.

Level	Entities	Concepts	Relationships	Propositions	Use Case
Low	3–5	1–3	2–4	2–4	Quick ingestion, simple docs
Medium	5–10	2–5	4–8	4–8	Default — balanced
High	All	All	All	All	Comprehensive analysis
🎛️ Extraction Mode
A per-provider preset (extraction_mode) that tunes the Knowledge Service's extraction strategy. Set it when creating or editing a Context Provider, or per ingest job. Default is balanced.

Mode	Behaviour
fast	Fewest passes, minimal density — quickest ingestion. Captures only the most salient entities & relationships.
balanceddefault	Balanced coverage vs. speed. Recommended preset for most documents.
max_extraction	Maximum density — extracts every entity, concept and relationship the model can find.
deep	Multi-pass, thorough reasoning. Highest recall on long or complex documents.
fact_dense	Optimized for dense factual propositions (triples). Best for spec / reference material.
precise	High-precision — favors accuracy over recall. Fewer but higher-confidence extractions.
auto	Picks a preset automatically based on document characteristics.
🛠️
Modes are defined in config.yaml and map onto the extraction density and entity / relationship taxonomy used by the Knowledge Service — adjustable without code changes.
🔗 Semantic Resolution
During the Knowledge Service stage, each new node is embedded and compared against existing nodes via the GN index; close matches are merged instead of duplicated.

Node Type	Embedding Input	Example
Entity	{label}: {description}	BT Group: British telecommunications company
Concept	{name}: {definition}. Also known as: {aliases}	MRC: Monthly Recurring Charge. Also known as: Monthly Fee
Procedure	{name}: {intent}	Circuit Decommission: Decommission and cease billing
Step	{description}	Notify carrier of pending decommission and request cease date
🔑
Entity merge threshold: 0.85. Concept merge threshold: 0.82.

crawl depth = 1	Page + all same-domain links found on it
crawl depth = 2	Page + links + links from those pages

Knowledge Graph
The graph stores entities, concepts, procedures, and their relationships in Neo4j. Every node also has an embedding signature in the GN vector index with a direct neo4j_id link.

🏗️ Node Types
🏷️ Entity
Named things: people, orgs, circuits, devices, locations
e.g. BT Group, CID-44821, LON-CE-01
💡 Concept
Definitions and terms with aliases
e.g. MRC (Monthly Recurring Charge)
📌 Proposition
Factual triples: (subject, predicate, object)
e.g. (CID-44821, has_bandwidth, 100Mbps)
📋 Procedure
Named SOP with intent. Parent of Step nodes.
e.g. Circuit Decommissioning and Billing Cessation
▶️ Step
Individual step in a procedure DAG
e.g. Step 3: Remove circuit config from edge routers
📁 Document
Ingested file. Connected to Chunks via CONTAINS.
e.g. contract.pdf, decom_sop.txt
📄 Chunk
Text segment from a document. Stored in KS with embedding.
e.g. 512-token segment with heading context
🗄️ TableSchema
DDL table with column descriptions
e.g. circuits (circuit_id, bandwidth, carrier)

Querying
Questions are answered by semantically anchoring into the knowledge graph, expanding the neighbourhood, retrieving source chunks, and generating a grounded answer.

🔍 Query Flow
Embed
Question → vector
→
Search GN
Semantic anchors
→
BFS
Neo4j traversal
→
Search KS
Chunk retrieval
→
Search PS
Procedures
→
LLM
Generate answer
Step	What Happens	Key Detail
1. Embed question	The question is embedded using the configured embedding model	Same model used for node embeddings
2. Search GN	Semantic search against graph node index. Returns nodes with neo4j_id directly.	Threshold: 0.40. No fuzzy lookup needed.
3. BFS Expansion	From anchored nodes, expand neighbourhood in Neo4j up to N hops	Returns both nodes AND edges (reasoning subgraph)
4. Search KS	ANN search in Milvus KS for semantically relevant document chunks	Top-K chunks (default 5)
5. Search PS	ANN search in Milvus PS for relevant procedures	Included if similarity ≥ 0.75
6. LLM Answer	Graph context + chunk context + procedure context → LLM generates grounded answer	DSPy ChainOfThought with AnswerSignature
🧠 Reasoning Subgraph
Every query response includes a reasoning_subgraph — the exact nodes and edges the system traversed to answer the question.

Field	Description
nodes	All nodes in the traversed subgraph (with properties)
edges	All edges connecting those nodes (source, target, type)
anchor_node_ids	Which nodes were the semantic search entry points

Explainability & Observability
Every query is fully traceable. A Retrieval Pass Card scores each stage of the retrieval pipeline, and a Reasoning Trace shows the exact graph path, document chunks, and procedures the system used to produce its answer.

🎴 Retrieval Pass Card
Open it from any row in the Explainability response-trace table. It walks the same five stages the query engine ran, each with a 0–100 score and its own quality + risk signals.

LLM answer
Stage	What it measures	Signals
Knowledge Store	How many document chunks were retrieved and how relevant they are	Retrieval confidence, avg similarity, coverage, source diversity · Risks: hallucination, knowledge gap, noise
Context Graph	How the query anchored into the graph and which entities/relationships were traversed	Entity match, relationship confidence, graph relevance, completeness · Risks: contradictions, missing context, fragmentation
Procedure Store	Which SOP(s) the query consumed and the exact steps used	Match score, step coverage, execution readiness, policy alignment · Risks: ambiguity, missing steps, failure risk
Fusion Layer	How the three stores were combined into one confidence	Cross-source agreement, consistency, source balance · Risks: conflict, signal entropy
Generation	How well the LLM grounded its answer in the retrieved context	Groundedness, faithfulness, answer relevance, citation coverage, completeness · Risks: hallucination, model uncertainty
🎨 Confidence & Risk Scoring
🎚️
All scores use one colour scale: 0–40 red, 40–70 orange, 70–100 green.
Signal type	How to read it
Quality signals	Higher is better — confidence, similarity, groundedness, coverage. Green = strong.
Risk signals	Shown as the actual probability, where lower is better — hallucination, missing context, ambiguity. Green = low risk.
Confidence ring	The query's final blended confidence (Fusion-weighted across all stores).
🧭 Reasoning Trace
The graph-trace modal (the graph tag on a response row) opens three tabs:

Trace
The tool calls and the ordered graph-traversal steps from the semantic anchors outward, each with a per-hop confidence.
Graph
An interactive force-directed view of the reasoning subgraph — nodes coloured by type, anchors highlighted.
Answer
The query, final confidence band, and the generated answer text.
🔑
The trace is reconstructed from the query's graph_path (nodes, edges, anchor_node_ids) stored on every tristore_query_events row.
📋 Procedure Consumption
The Procedure Store tab shows which SOP(s) this specific query consumed and the exact steps it used — reconstructed from the Procedure and Stepnodes in the query's graph path, linked by HAS_STEP edges.

State	What you see
SOP used	The procedure name, version, and the ordered "Steps consumed" list with a match score.
None used, store has SOPs	A compact note with the count of SOPs available in the store (informational queries don't trigger an SOP).
Store has no SOPs	An empty state — nothing was ingested as a procedure for this provider.
🔢 Token Usage
Source	Behaviour
Exact	Summed from llm_logs where job_id = query_id and query_type = 'query' — the real prompt/completion tokens for that query's LLM calls.
Estimated ~	When a query has no linkable LLM log, tokens are estimated from the retrieved context size and answer length (≈ 4 chars/token) and shown with a ~ and an "estimated" note.
✅
For exact tokens everywhere, the query service must write a query_id on each tristore_query_events row and reuse it as the llm_logs.job_id for that query's LLM calls.
